# Sub2API 升级经验与发布说明（2026-09-09）

本次发布把模型目录适配、用户侧引导修正和 Veyra 登录回跳修复收敛到同一条升级基线。文档用于后续升级和回归时复用，不记录 VPS 凭据、API key、跳板机信息或其他敏感配置。

## 1. 本次保留的功能

### 1.1 Veyra 登录回跳 404

问题表现：用户从登录页完成认证后，浏览器跳转到 `/_veyra/return?...`，页面显示 Vue Router 的 404；返回首页后账号实际已经登录。

根因是 `/_veyra/` 由后端门户中间件提供，不属于 Vue Router 的前端路由。登录成功后使用 `router.push()` 会把后端路径交给 SPA 的 catch-all 404，而认证会话已经在此前成功写入。

保留的实现规则：

- 统一由 `navigateAfterLogin()` 判断回跳目标。
- `/_veyra/` 目标使用完整文档导航，让后端门户和它自己的 `app.js` 处理 `home`、`console` 或 Alchemy 目标。
- 普通 `/dashboard` 等应用内路径继续使用 Vue Router，避免不必要的整页刷新。
- 密码登录、Passkey 登录和 2FA 验证三个成功分支全部复用同一逻辑。

### 1.2 模型目录、上游映射与引导页

模型相关调整继续以既有模型目录提交为准：

- GPT-5.4、GPT-5.4 Mini 从默认公开目录、活动映射和新生成的 OpenCode 配置中移除；历史账单、用量和兼容读取逻辑不做破坏性清理。
- GPT-6 Astra 只加入已通过对应上游 `/v1/models` 能力核验、且确实处于活动调度范围的账号，不把“理论支持”当作可用能力。
- GPT-5.5 作为通用文本回退和测试默认模型；SmartRouter 的探测优先使用已确认映射的 GPT-6 Astra，再回退到其他活动模型。
- DeepSeek、Doubao/Ark、Kimi 等非 OpenAI 上游保持自己的分组目录和默认模型，不再让引导页无条件显示 GPT-5.5。
- 普通用户 DTO 只下放分组公开模型列表和默认映射模型，不下放账号凭据、内部路由结构或上游密钥。
- OpenAI-compatible、Gemini、Anthropic 和 CCSwitch 的引导地址按协议归一化；OpenAI-compatible 使用 `/v1`，Gemini 使用 `/v1beta`，避免旧版“只有域名”或重复 `/v1/v1`。

## 2. 升级时必须保留的工程经验

### 2.1 先验证能力，再改模型目录

新增模型或恢复旧模型前，先对活动账号执行上游模型能力审计，并同时核对账号映射、分组 `models_list_config`、前端生成器和价格配置。模型下架时先从公开目录和活动映射移除，历史用量与账单保留。

### 2.2 应用镜像与数据变更分离

应用代码升级优先只替换应用容器，使用 `up -d --no-deps`，不重建 PostgreSQL 和 Redis。每次切换前保存：

- 变更前 compose 文件和应用容器 inspect 信息；
- PostgreSQL custom dump；
- Redis RDB；
- 旧应用镜像或可恢复的镜像 tar。

数据库快照只用于明确的数据变更回滚，并且需要业务窗口、停止应用和单独确认；不能把恢复数据库当作普通代码回滚步骤。

### 2.3 验收不能只看容器状态

每次发布至少验证四层：

1. 容器健康状态、应用 `/health` 和 `/setup/status`；
2. 登录页和新的登录资源是否为 200，且资源中确实包含回跳修复；
3. 直接请求 `/_veyra/return?target=home` 是否由后端门户返回 200；
4. API key 的 `/v1/models`、实际文本请求和非 OpenAI 分组的模型引导是否与活动配置一致。

### 2.4 二进制传输必须有完整性校验

经过跳板机传输大镜像时，不把一次长连接 SCP 成功作为依据。应采用可恢复的分段/原始流传输方式，目标机合并后计算 SHA-256，并与本地构建产物比对；校验通过后再加载镜像和切换 compose。

## 3. 回归基线

本次登录修复已验证：

- Veyra 回跳定向测试、AuthLayout 测试和 LoginForm 测试：8 个测试通过；
- 认证回归：16 个测试文件、129 个测试通过；
- TypeScript typecheck、ESLint、前端 build 通过；
- 两个已切换环境的 `/health`、`/setup/status`、登录页、登录资源和 Veyra return 入口均返回 200；
- 新登录资源同时包含 `window.location.assign` 和 `/_veyra/` 判断，旧 SPA 404 路径不再作为成功登录后的处理方式。

模型目录基线另有完整记录，包含模型列表、账号能力核验、GPT-6 Astra 映射和上游请求结果。后续若模型配置变化，应重新执行完整前端测试和至少一轮有效 API key 的 `/v1/models` 与实际请求验证。

## 4. 回滚原则

- 仅回滚登录/前端代码：恢复对应环境的变更前 compose 和应用镜像，只重启应用容器，不恢复数据库。
- 回滚模型映射或公开目录数据：先停止应用、核对 PostgreSQL/Redis 快照和业务窗口，再按记录恢复；恢复后重新检查 `/v1/models` 和计费相关接口。
- 回滚后必须再次验证首页、登录、Veyra return、健康检查和 API key 请求，不能只以容器为 running 作为完成标准。
