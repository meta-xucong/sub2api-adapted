# 执行、审计与发布计划

## 实施顺序

0. 固定HEAD、保存当前工作树状态与证据。若main变化，先重核差异和对应官方修复，不能盲套旧patch。
1. F01 fork审核一致性、F02确定失败收费资格、F03候选raw回归，分别小提交。F02牵涉官方代码但P1且依据充分，不能等到后期。
2. F07 fork预算接合与F06计数/F05终态/F04词法，各自提交。共享文件需串行集成，禁止多代理同时改同一文件后只按总测试掩盖冲突。
3. F08代理脱敏；之后F09 Tavily诊断契约；F10浏览器CSP。官方问题的补丁说明附公开依据，并保留上游变更可替换性。
4. 每提交：红绿反例、邻近回归、只读交叉审查；最终固定SHA跑组合套件、构建与安全门禁。
5. 正式CI/隔离部署/真实Provider及账单对账属于后续验收。不得因阶段1通过就宣告总体可发布。

## 审计清单

- 根因和修改位置一致，是否优先在fork适配边界解决？
- 是否把官方未合并PR当作发布事实？是否依据准确blob/函数而非恢复提交blame？
- 是否不必要改变解析、重试、价格、模型、权限或媒体超时？
- 是否给“错误已写出”错误赋予交付/计费资格？
- 是否漏掉其他入口、其他调度模式、持久设置、自定义配置？
- 错误/日志是否含原请求、key、URL凭据？
- 用例是否走真实handler/service/实际扣款命令，而非手工重写生产逻辑？
- 所谓“历史也有”是否仅静态证据，是否错误包装成历史实测？

## 交付材料

每次提交应交付：固定SHA、变更归属表、关联F编号、最小差异说明、准确测试命令/结果、失败尝试与环境skip、剩余风险、回滚说明。源码包manifest与提交对应，Windows工作树CRLF不能冒充Git blob变化。

本文档包是计划，不包含生产修复代码，也不应覆盖上一份源码包的身份。当前e5b9bfbe保持HOLD。

## 部署前门禁

- 全部P1和候选回归关闭；其他问题逐项修复或明确限定功能范围，不能口头忽略。
- 真实数据库/Redis、正式构建镜像与运行SHA一致。
- 逐模型/上游验证价格、尺寸、产物数量、断流/重试，生成调用的成本与测试账号事先批准。
- 实际反向代理头信任、持久开关、CSP、代理下载兼容与网络边界核验；配置改动另需批准。
- 共享custom voice隔离未解决时，不能宣称多人共享该能力安全。若需限制功能，必须单独批准，不能本次暗中关闭。
- 负载验证记录延迟、错误率、CPU/RSS、磁盘、活跃请求和计费队列，且有明确峰值/恢复观察窗口；健康200不是业务正确性证明。

## 回滚

本计划不设计schema迁移。保留原镜像/配置、记录新旧SHA和摘要；切换/回滚不得删除历史账单或重复执行生成任务。发生账单异常先停止扩量，保留审计证据再受控回滚；是否限制服务需另行批准。

回滚到有已知安全问题的旧版不能被写成“安全恢复”。若补丁涉及配置，不自动撤销管理员自定义策略；由切换清单记录并核验差异。
